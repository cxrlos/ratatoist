# ratatoist

A terminal client for Todoist, written in Rust with ratatui. One crate; the binary is `ratatoist`.

## Read first

- `GLOSSARY.md`: the words for what ratatoist shows and acts on. Use them in code, docs and issues; never use a term listed under _Avoid_.
- `docs/adr/`: the decisions in force, one file each.
- `docs/agents/`: issue tracker, triage labels and domain-doc rules.
- `docs/releasing.md`: how versions, tags and publishing work.

## Status

Active. Each milestone's work lands on a `feat/vX.Y.0` branch, which is squash-merged into `main` and ships as that minor version. Plans live in GitHub issues; repo files describe what exists.

## Critical rules

1. Never read, print, log or commit a Todoist API token or `.env` file. Tests never call the Todoist API; responses come from fixtures recorded from real responses, and a fixture that is not one is named `HYPOTHETICAL_*`.
2. The PR title is the commit: a Conventional Commit, with `!` for breaking changes. Squash merge only.
3. release-plz owns `CHANGELOG.md` and the version in `Cargo.toml`. Never edit them by hand.
4. Never accept a changed insta snapshot without showing the `.snap.new` diff first. Generate every pending snapshot in one run with `INSTA_FORCE_PASS=1 INSTA_UPDATE=new cargo test --locked --no-fail-fast`, review them, then accept once.
5. `main` and every `feat/vX.Y.0` branch are shared: add commits on top, never rewrite them. Every CI job and the `.claude/settings.json` format hook gate each change; fix what they flag instead of bypassing them.
6. MSRV is 1.88 (edition 2024; ratatui 0.30 needs it). A dependency or language feature that raises it needs an ADR.
7. Linux and macOS only. Do not add Windows-specific code paths.

## Workflow

1. Orient: read the issue, `GLOSSARY.md` and the relevant ADRs. Branch `<type>/<issue>-<slug>` off `main` (during a milestone, off `feat/vX.Y.0`).
2. Agree seams: name the module and public interface you will touch before writing code.
3. Red then green with `/tdd`. After each slice, run that test target and `cargo clippy`.
4. Verify: every command under Commands passes.
5. Review: `/code-review` against the merge-base.
6. Write back: fill in `.github/pull_request_template.md`, with `Fixes #N` or `Part of #N`.

Done when someone reading only the issue and the PR could pick up the next piece.

## Design principles

These are targets. New code meets them; older code is brought up to them as it is touched.

- Rendering is a pure function of app state; every screen has a `TestBackend` + insta snapshot.
- All Todoist API access goes through one module, so tests swap it for fixtures.
- One action registry drives key handling, the keymap config, the `?` cheatsheet, the bottom-bar hints and the palette. Never list a key binding anywhere else.
- No `unwrap`/`expect` outside tests; errors carry context to the screen, and a network failure keeps the data already loaded.
- Every style comes from a `Theme` method named for its role (`due_overdue`, `error_border`), so built-in and user themes reach every widget.
- Text is measured and cut only through `src/ui/text.rs`: widths in terminal cells, and cut text ends in `…`.
- The terminal is restored on every exit path, panics included.

## Map

When you add, move or split a module, update its entry here in the same PR.

- `src/main.rs`: the `ratatoist` binary. Parses the CLI and either runs an `auth` command or loads the config, starts logging, resolves the token, paints from the cache (`runtime::paint_from_cache`) and runs the app against `HttpClient` with the config and cache folders as `runtime::Files`, with the release check unless `[updates]` or `RATATOIST_NO_UPDATE_CHECK` turns it off. With `--demo` it runs against `demo::client`, the demo account through `FakeClient`, and reads and writes nothing in the config or cache folder. With no token it starts the app on its Not logged in screen, which syncs nothing and reads and writes no cache; any other startup error prints as its plain message on stderr, after the terminal is restored, and exits 1.
- `src/lib.rs`: the library root, so tests import `ratatoist::...`.
- `src/app/`: the core. `State` (`state.rs`) is everything the screen shows and nothing else: no client, channel, terminal or file handle; `today` and `now` come from the runtime, and `keymap` is the `Keymap` in force. `State::screen` is the tab shown (Inbox, Today, Upcoming, Projects, Labels) and `active_pane` its list, the Projects tree or a task's detail; `wide_layout_columns` is where the list and detail start to show side by side. Overlays are a `Modal` stack (`modal.rs`); the top one takes keys, all of them are drawn bottom to top, and a `Modal::WhichKey` on top holds the chord typed so far. `browse.rs` holds the Projects and Labels screens: `tree_rows` (the personal space then each workspace and folder, the Inbox left out, a folded folder hiding its projects), `label_rows` (the user's labels, favourites first, then shared ones, each with its open-task count), the focus kept by id in `tree_focus` and `label_focus`, Enter opening the focused project's list or the opened label's tasks grouped by project, Esc coming back to the same row, folders folding and `s` marking a favourite optimistically (`rolled_back_projects` marks a rejected one). `palette.rs` is the palette: `palette_matches` fuzzy-finds (nucleo-matcher, case-insensitive, by score, actions first on ties) the actions that apply under it and can run, the loaded open tasks and the projects; Enter runs the action through `perform`, focuses the task in its project's list or opens the project's list. `update(&mut State, Event) -> Update { redraw, effects }` (`update.rs`) applies one `Event` (`event.rs`) and returns the `Effect`s (`effect.rs`) for the runtime to carry out, each documenting the `Event` that answers it; keys go through `on_key` (see `src/keys/`) and `perform` carries out each `Action` (`action.rs`, with `Editable`, the task field an `Action::Edit` changes). Every text input is one prompt (`prompt.rs`): `open_prompt(state, PromptField)` opens a `Modal::Prompt` for a comment or the focused task's content, description or due date, taking the task when it opens; content and description start with their text, a comment and a due date empty. Enter sends it, or keeps it open with the reason when the text cannot be sent (no content, no comment, no due string); the next edit of the line drops the reason. Its text is a `TextField` (`text_field.rs`, one line with a cursor, edited by typed keys, `C-w`, `C-u` and bracketed paste), and `State::edit_task` holds the task an open prompt or priority picker writes to. A due string sent stays in `State::pending_due` until Todoist answers with the task, so the task can show what was typed meanwhile. Every choice goes through one picker (`picker.rs`): `open_picker(state, PickerKind)` builds the entries (priority, sort, list filter, the add-task form's project, theme) with the value in force marked, typing filters them, 1 to 9 pick among what is left, choosing a sort or list filter keeps focus on the same task while it stays visible, and choosing a theme applies it and returns `Effect::SaveTheme` with its slug (none while `State::no_color`); its answer, `Event::ThemeSaved`, shows a notice when `config.toml` was left alone and reports a failed write. `State::list_filter` and `State::sort` hold the list filter and sort; Esc on the list clears a list filter, and switching screens resets it. Choosing completed or all on a project's list loads that project's newest window of completed tasks into `completed_cache`; the keyless `load-older-completed` action loads the window before `State::oldest_completed`, adding the tasks not already there, with a notice of how far back they now go. `confirm.rs` asks before work is lost: while `temp_id_pending` holds commands Todoist has not answered, `R` and `q` push a `Modal::Confirm` (title, subject, consequences, verb, and the `Confirmed` it runs on `y` or Enter; `n` or Esc closes it); with none pending they run at once. Completing a task never asks. The add-task form (`task_form.rs`: `TaskForm` and its `FormField` rows, content, priority, due and project) opens on the project in view, else the Inbox, due `today` on Today; Tab and S-Tab move between rows, Enter adds the task from a text row (or keeps the form open on the content row with the reason when it is empty, until the next edit or row move) and opens that row's picker on the priority or project row, and the new task shows at once under a temp id. The content goes as typed: `item_add` reads no priority, label or project out of it. `State::store` (`store.rs`) holds every synced entity by id (tasks, projects, sections, labels, workspaces, folders and reminders in `Table`s, `reminders_of` giving a task's, which keep arrival order, find by id in constant time and take a new stamp on every write; the comments by task, the user and collaborators), serde-serializable as is; `Store::merge` replaces what a full sync carries and upserts or deletes by id from a delta. `view.rs` derives what shows: the visible tasks of the current screen (the Inbox or a project's tasks, Today, the next seven days for Upcoming) narrowed by the list filter and sorted, under their group headers (`list_rows`), the counts and the label rows. They are built once into `Lists` (task rows as positions, the parent tree with depths and completed descendants) and rebuilt on the first read after a store stamp, `collapsed`, `completed_cache` (both `Stamped`) or the list state changes, so frames and keys read them. Every parent walk stops at a task or project it has seen: tasks on a parent loop show at top level, and `sync.rs` logs each new loop once as an `ErrorKind::ParentCycle` failure after a merge. `load_error` holds why the tasks cannot load at all (no token, token rejected), and `State::indicator` gives the sync indicator from `sync_health`, `live` and `last_sync_at` (`live`, `polling` or `idle` with the time since the last sync, or `offline` or `sync failing` as an alert), or none while `load_error` fills the body with its screen. `live.rs` decides when ratatoist syncs on its own: a live message that is not a keep-alive asks for `Effect::ScheduleLiveSync`, and the `Event::LiveSyncDue` that answers it 2 s later runs one sync for the whole burst; while the connection (`LiveLink`) is not up and the account is loaded, a tick runs a sync every 60 s, a reconnect stops that and syncs once to catch up, and idle pauses both until the first key, which syncs once. Each of these syncs is `State::background_sync_request`: incremental, or the startup sync's full read while the token is `*` or no user is known, as after a failed first sync. `failure.rs` holds the `Failure` (its `ErrorKind`, mapped from a `ClientError` or a `sync_status` error, with a summary and a fix; the action, as `complete "Buy oat milk"`; the time and the raw message) and the `ErrorLog` behind the messages log, where a failure equal to the newest entry (kind, action, message) only moves that entry's time: `State::report` logs a failure and makes it the notice until the next key (writes the user asked for and the first sync answer), `State::log_failure` only logs it (later syncs, the live connection, comments and completed tasks). No failure pushes a modal. `sync.rs` merges sync responses and runs optimistic writes: a write applies locally, records a rollback snapshot in `temp_id_pending` keyed by command uuid and returns `Effect::SendCommands` with that one command, which the runtime sends with the sync token and the incremental resource types (`command_request`), so the answer carries what changed since that token; the answer settles its commands, maps temp ids (v4 uuids), then merges like an incremental sync and its token is taken. Completing a recurring task leaves it open with its due string in `pending_due` until that answer brings the next date. A rejection or a failed flush restores the snapshot, reports the failure and keeps it in `State::rolled_back`, so the task's row shows the failed mark and its detail the reason until the task changes again. The first sync asks everything a full sync does since `State::sync_token`, which is `*` unless `paint_from_cache` filled the store; the first sync that succeeds, whenever it comes, is checked against `cache_user_id`: naming another user drops the store for a full sync, and an answer without the user asks for it once (`Effect::FetchUser`, answered by `user_fetched`), which runs the same check and opens the live connection, or logs a failure and leaves the check to the next sync that succeeds. The live connection opens on the first answer that gives its URL. A dated full sync (`full_sync_date_utc`, a big account's possibly lagging data) is followed by one incremental sync. Each merge marks the cache dirty, and a tick asks for `Effect::SaveCache` once `CACHE_DEBOUNCE` has passed and no command is unanswered. Invariant: one command per flush, because the snapshots are absolute `before` values that do not compose when same-task edits share a flush. An incremental delta parks tasks still in `temp_id_pending` in `State::parked`, applied when their last write settles (after a rollback's snapshot, since newer); rolling back a write rebases later writes to the same task or project onto its snapshot. After a merge the focus stays on the task it was on while that task is visible, else the nearest row; a detail that then shows another task loads its comments as opening it does. `App<B: Backend>` (`mod.rs`) owns the `State` and the `Terminal`, draws only when an update asks, and counts frames.
- `src/keys/`: every key binding, and nothing else binds one (`tests/keys.rs` fails on a `KeyCode::Char` match outside it). `registry.rs` is the `ACTIONS` table (id, label, group, hint, contexts, default vim keys, availability) and the `STANDARD` preset's changes; `key.rs` the `Key` and `KeySequence` notation (`<C-d>`, `gg`); `keymap.rs` the `Keymap` built from a `Preset` and the `[keys]` overrides (replace, prepend, append, noop), which resolves a key sequence in the active contexts to a binding or the start of a chord; `reference.rs` `keymap_reference()`, which generates `docs/keymap.md` (`UPDATE_KEYMAP=1 cargo test --test keymap_reference`); `mod.rs` the `Context`s and `active_contexts`/`screen_contexts`, which map the top overlay or the screen and its focused pane to them (only Everywhere while the first sync runs or the tasks cannot load). Dispatch lives in `src/app/update.rs`: `on_key` lets the focused text field take printable keys, edits and bracketed paste first (`type_text`), then `press` resolves the key through `State::keymap` and the chord held in a `Modal::WhichKey`, and `perform` carries out the `Action`.
- `src/runtime.rs`: the async loop and the one place that reads the clock, through `clock()`; clippy's `disallowed-methods` (in `clippy.toml`) rejects jiff's `Zoned::now`, `Timestamp::now` and `TimeZone::system` anywhere else, so the zone too comes only with `State::now`. It builds the first `State` from `Config`: the `Keymap` from `[keys]`, the icon set, the themes, and `NO_COLOR`, read once at startup, which swaps every theme for `Theme::no_color`. It also reads the old `ui_settings.json` on each start and never writes it: its theme and idle timeout apply only where `Config` sets none, with a notice naming the `config.toml` lines that keep them. It then reads crossterm's `EventStream`, the shutdown future and a one-second tick, and carries out each `Effect` against a `TodoistClient`: a request runs in its own tokio task and comes back as an `Event` over an mpsc channel, except `/sync` reads and command flushes, which the sync lane runs one at a time in the order sent so answers land in the order Todoist handled them; the live connection forwards each message as `Event::Live`; files go to the `Files` `main` passes, or nowhere when it passes `None`, through the one writer, a task that runs each `Save` (the cache, the old sync token's deletion, the release cache, `[theme] name` through `config_write`, answered as `Event::ThemeSaved`) on the blocking pool in the order sent and that `run` waits for before it returns, so the last of each is on disk. `Effect::SaveCache` writes `Cache::of` the state, or deletes the file when that is `None`; however the loop ends, the state's `unsaved_cache` is written last. `run_checking` also takes the `ReleaseCheck`: a tick passes the clock to `ReleaseState`, which asks for a check when one is due, and the runtime asks GitHub in its own task and opens URLs through `browser`.
- `src/release.rs`: the release check (ADR 0002). `ReleaseSource` asks GitHub's `releases/latest` (or a test server's URL) with no token; `ReleaseCache` keeps the `Record` (last check, latest and skipped version) in `release.json` in the cache folder, written atomically; `Channel` reads the install channel from the binary's path; `background_check`, which every start calls (`--demo` too), builds it only for the TUI on a real account with nothing turning it off (`off_switch`, `checks_in_background`). The app's side is `src/app/release.rs` (`ReleaseState`: the notice, the skip, the upgrade hint).
- `src/browser.rs`: opens a URL with `xdg-open` or `open`, detached from the terminal.
- `src/todoist/`: all Todoist access, behind the `TodoistClient` trait in `mod.rs` with the typed `ClientError`. `http.rs` (`HttpClient`, the reqwest client: Bearer token, 30 s and 10 s timeouts, 429 retries honouring `Retry-After` and `error_extra.retry_after`; `ClientConfig` points it at a test server), `live.rs` (the WebSocket behind `live_events`, a stream that never ends: text and binary messages are changes, pings and pongs nothing; it pings every 30 s and drops a socket silent for 75 s, pongs included, then reconnects a second after a drop, or, while connecting fails or a socket drops within 30 s of opening, backs off from 5 s up to 60 s with up to half of each wait cut at random), `fake.rs` (`FakeClient`: serves JSON fixtures, records every command and counts reads, fails chosen ones, can hold every sync unanswered, plays a scripted live connection), `demo.rs` (the demo account, built at a given moment so its dates read right on any day and its local times in that moment's zone, with the fixed `demo::NOW`, a civil date and time, for tests; and `DemoClient`, a `FakeClient` that applies each command to the account so writes last for the session and serves comments and completed tasks per task, project and window), `model.rs` (the serde types: every field but an id has a default and every enum, as `DurationUnit` and `ReminderKind`, an `Other` variant, so a drifted entity never fails a sync; `Deadline`, `Duration` and `Reminder` are typed), `sync.rs` (sync requests, commands and responses). Fixtures live in `tests/fixtures/todoist/`. Reads and writes go through `POST /api/v1/sync` with a sync token (`*` for a full sync, otherwise an incremental one); both read `reminders`, and neither `reminders_location`. Comments and completed tasks are cursor-paged, with every query parameter encoded by reqwest. Completed tasks come from `GET /tasks/completed/by_completion_date` one `CompletedWindow` at a time: twelve weeks, `since` inclusive and `until` exclusive as UTC midnights, the newest ending two days after `today` so a task completed late today counts in any time zone.
- `src/cli.rs`: the clap CLI: `--demo` and `auth login [--stdin] | status | logout`.
- `src/auth/`: the token. `token.rs` (`ApiToken`, redacted in `Debug` and `Display`, revealed only by `expose()`), `keyring.rs` (the `Keyring` trait, `OsKeyring` on the macOS Keychain or the Linux Secret Service under service `ratatoist`, and `MemoryKeyring` for tests), `migrate.rs` (the one-time move of a legacy `api_token` out of `config.toml`, which removes that line through `config_write::replace`), and `mod.rs` (resolution: `TODOIST_API_TOKEN`, then the keyring; and the `auth` commands, which `run` hands to `run_with` with the real keyring, environment, client and console, so tests pass their own and capture what is printed; keyring, stdin and terminal prompt calls run on the blocking pool). `docs/auth.md` describes it for users.
- `src/paths.rs`: the XDG config, state and cache folders (`~/.config/ratatoist` and friends), on macOS too.
- `src/config.rs`: reads `config.toml` (`[ui] icons` and `wide-layout-columns`, `[keys]` with its `preset` and `[keys.CONTEXT]` tables, `[theme] name`, `[sync]`, `[updates]`) and the Base16 theme files in `themes/` beside it into `Config`, never writing either; `src/config_write.rs` holds the one write. Every problem is a warning `config.toml:LINE:COL: problem` and only its section falls back to defaults; in `[keys]`, a bad binding resets only its `[keys.CONTEXT]` table and a bad `preset` the whole table. A theme is found by its name with case, spaces and hyphens ignored. Falls back to the old macOS folder with a warning; `Config::dir` is the folder read, where the picked theme is written and the old settings are found. `docs/config.md` lists every key.
- `src/config_write.rs`: the one key ratatoist writes in `config.toml`, `[theme] name` (ADR 0004). `save_theme` edits it with `toml_edit`, keeping every other byte, creates a missing file or table with just that key, follows a symlink to its target, and leaves a file that does not parse (or whose `theme` is not a table) alone as `ThemeNotSaved::Refused`; `replace` is the atomic write (a temp file with the file's mode, renamed over it) the token migration uses too.
- `src/cache.rs`: the local cache (ADR 0003). `Cache` (schema version, user id, sync token, the whole `Store`, reminders included; never the API token) in compact `cache.json` in the cache folder, written atomically with mode 0600 through a temporary file named with the process id; `load` gives `None` for a missing, unreadable or other-version file, which means a full sync. `remove_old_sync_state` deletes the `sync_state.json` versions before 0.8.0 kept in the config folder.
- `src/terminal.rs`: the terminal guard, the one owner of raw mode and the alternate screen. `Guard::enter()` takes the terminal; dropping the guard, or a panic while it lives, restores it, the panic hook doing so before the message prints. `shutdown_signal()` resolves on SIGINT, SIGTERM or SIGHUP, which the runtime turns into `Event::Shutdown`. `tests/pty.rs` checks all of this against the real binary in a pseudo-terminal.
- `src/logging.rs`: `tracing` as JSON lines to `ratatoist.<date>.log` in the directory `main` passes (`paths::state_dir()`), rolled daily and keeping seven files, never to the terminal. The level comes from `RATATOIST_LOG` (an `EnvFilter` string, default `ratatoist=info`); `RUST_LOG` is ignored. tungstenite's handshake is never logged. `init` returns the `WorkerGuard`, which `main.rs` holds until the app returns.
- `src/ui/`: rendering, a pure function of `State`: `draw(&mut Frame, &State)` (`ui.rs`) draws the frame from `areas`: the tab row (`[1] Inbox │ [2] Today …` from the keymap, shrinking to `[n]` when it does not fit and cut with `…` below that, the release notice (`release.rs`, only while every tab's full title fits beside it) and the sync indicator at the right), the body of the current screen, the notice (0 to 3 rows), every modal in the stack bottom to top, then the bottom bar. `ui.rs` also holds `popup_block`, `centered`, `close_hint` (a popup's bottom border) and the sizes other code needs (`body_area`, `list_rows`, `detail_rows`, `messages_max_scroll`, `cheatsheet_max_scroll`). Overlays draw over the body only, on `Clear`, so nothing behind a popup shows through. The notice shows the newest failure in the error style until the next key, or else `State::notice`, muted; `messages.rs` draws the messages log `!` opens. The body shows the loading line or an error screen until the tasks are in (`error.rs`), then the Projects tree or the labels (`browse.rs`: lrat's browse rows, a marker, the name and a muted open-task count; the tree with the personal space, then each workspace, folders with their fold glyph, projects indented with `★` or `#` in their colour, and the failed mark on a project whose write was rolled back), or a task list: `list.rs` places the panes (lrat's `panes`, `Focus` and `pane_block`: from `State::wide_layout_columns` the list and the focused task's detail side by side at `Fill(3)`/`Fill(2)`, below it only the focused one; a focused pane has a thick accented border, the other a muted one, a pane alone a plain one), draws the list filter header when the filter or sort is not the default, the group headers and the task rows in columns (`row_cells`, `render_row`: marker, check or fold, content and muted marks with the deadline mark in its own style (only its glyph when its date would be cut), due in what the content leaves past its 30 columns, cut with `…`, priority, and the project on Today and Upcoming), and one muted sentence for an empty list; Upcoming groups by day (`upcoming.rs`). `detail.rs` builds the detail as lines wrapped to the pane, so scrolling counts real rows (content, field block with Deadline, Duration and the time reminders only when the task has them, description, subtasks, comments, details), with the breadcrumb as its title; a prompt on the task whose detail shows draws in place of its field (`list::prompt_in_place`, never while loading or on an error screen), and the detail takes the focus while it does. The picker (`picker.rs`: lrat's `render_with`) draws every choice list in the app. The confirmation (`confirm.rs`) shows its keys in the bottom border from the keymap. No clock reads; dates compare against `State::today`, and a due with a fixed timezone, an instant in UTC, falls on its day in the zone of `State::now`. The bottom bar (`hints.rs`: three labelled rows `Move`, `Do`, `Edit` or `View`, built only from `ACTIONS` and `State::keymap` for the active contexts, unavailable keys muted, `hints::render(state, frame, area)` draws into any `hints::ROWS`-row area; no view or component writes a key hint), the `?` cheatsheet (`cheatsheet.rs`: panes `Move`, `Edit the task`, `App` and the context's own keys from `ACTIONS`, up to four columns when wide, one scrolling column when narrow, then the release line with its upgrade hint, cut to the grid's room), the which-key popup after a chord prefix (`which_key.rs`, bottom-right of the body), the palette overlay (`palette.rs`: query line, rule, rows with keys right-aligned), dates, deadlines, durations and reminders as text (`dates.rs`), text measured and cut in terminal cells (`text.rs`), styles (`style.rs` and the role methods on `Theme`), themes (`theme.rs`: the colour roles views draw with, the `terminal` default, the ten Base16 built-ins under `src/ui/themes/` and user files, the muted contrast lift and `Theme::no_color` for `NO_COLOR`; no `Color::` literal outside it and `icons.rs`), glyphs (`icons.rs`: the Unicode and Nerd sets `[ui] icons` picks, read through `State::icons()`; no view writes a state, priority, fold, comment or project glyph itself), the prompt (`prompt.rs`: lrat's prompt over the body, the field and task in its title, the due date in force on a `Now` line, the `>` line being typed with the cursor kept in view, and what the field takes or why Enter was refused; `input_line` and `hint_line` draw the same two lines in place for a view that shows the field, `typed_line` and `kept_line` the `>` line of any field with and without the cursor) and the add-task form (`task_form.rs`: the prompt's look stacked, one row per field with the focused label accented, titled with the project it adds to, `Enter add` or `Enter choose` in its bottom border as the focused row takes text or a pick).

## Commands

```bash
cargo fmt --all --check
cargo clippy --all-targets --all-features --locked -- -D warnings
cargo test --locked
cargo insta pending-snapshots
cargo +1.88 check --all-targets --locked
cargo deny check
cargo package --locked
gitleaks git --redact
cargo run -- --demo
```

CI runs all of these except `cargo run` on every PR, with tests on Linux and macOS. `gitleaks git` is the local form of CI's full-history secret scan. `cargo run -- --demo` needs no token, keyring or network.

## Agent skills

### Issue tracker

GitHub Issues on cxrlos/ratatoist, through the `gh` CLI. See `docs/agents/issue-tracker.md`.

### Triage labels

The five default labels: needs-triage, needs-info, ready-for-agent, ready-for-human, wontfix. See `docs/agents/triage-labels.md`.

### Domain docs

Single context: `GLOSSARY.md` and `docs/adr/` at the repo root. See `docs/agents/domain.md`.
